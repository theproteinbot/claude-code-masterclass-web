Canonical Capstone Markdown

Capstone Project (Self-Paced Learner Edition)

This capstone consolidates the course into one structured project. You will frame the problem, run phased execution, capture evidence, and self-assess your workflow quality using RUBRICS.md.

TOC Mapping (Required)

  • TOC 1: Claude Code operations, Git workflow, permissions, session controls
  • TOC 2: task framing, clarifying questions, acceptance criteria, eval design
  • TOC 3: refactor/review/orchestration techniques
  • TOC 4: context engineering and progressive disclosure
  • TOC 5: optional Codex transfer comparison

Capstone Scenario (Default)

You are given a small-to-medium codebase (or a selected module in your own repo) with at least one real issue and one maintainability problem. Your goal is to complete a constrained improvement sprint that demonstrates:

  • problem framing
  • safe execution
  • verification discipline
  • recoverability
  • workflow explainability

Pick one scope:

  • A bugfix plus a behavior-preserving refactor in the same area
  • A feature tweak plus tests/checks and cleanup
  • A reliability improvement (tests, error handling, validation) plus workflow documentation

Deliverables (Required)

  • A written problem statement (scope, non-goals, assumptions)
  • Acceptance criteria and verification plan
  • Execution plan with phases/checkpoints
  • Code changes in one or more commits (prefer small, reviewable commits)
  • Verification evidence (tests/lint/manual repro)
  • Diff summary and risk notes
  • Self-assessment using the capstone rubric in RUBRICS.md
  • Retrospective notes (what worked, what failed, what to reuse)

Success Criteria (Learner-Facing)

  • You meet the stated acceptance criteria or clearly document what remains and why
  • Your diff is scoped and explainable
  • Your verification evidence is reproducible
  • Your workflow choices (context resets, tool use, approvals, recovery steps) are deliberate
  • Your retrospective identifies at least one reusable workflow improvement

Advanced Variants (Optional)

Variant A - MCP-Assisted Research

Use a read-only MCP workflow to gather supporting context (docs/schema/search) before coding. Write the trust boundary and verify all tool-derived facts locally. [Source: https://docs.anthropic.com/en/docs/claude-code/mcp] [Source: https://modelcontextprotocol.io/specification/2025-06-18]

Variant B - Subagent/Hook Pipeline

Split discovery, execution, and review into distinct roles or automation gates. Keep the scope small enough that you can explain each boundary clearly. [Source: https://docs.anthropic.com/en/docs/claude-code/sub-agents] [Source: https://docs.anthropic.com/en/docs/claude-code/hooks]

Variant C - Codex CLI Transfer Compare

Re-run one capstone phase with a Codex-style tool and document which workflow pieces transfer unchanged (scope, criteria, verification) vs which are tool-specific. [Source: https://github.com/openai/codex] [Source: https://platform.openai.com/docs/guides/codex]

Beginner Variant (Scaled)

If the default capstone feels too large, scale it down:

  • Choose only one bugfix or one refactor (not both)
  • Use 3 phases instead of 5 (framing, execution, review)
  • Require the same evidence quality, just smaller scope
  • Score yourself with the capstone rubric anyway

Capstone Prompts (Starter Templates)

Discovery Prompt

Inspect the relevant files for this task and propose a short plan. Ask clarifying questions first if anything is ambiguous. Define acceptance criteria, non-goals, and how you will verify success. Wait for approval before editing.

Execution Prompt

Execute the approved plan in small steps. After each step, summarize the diff, note likely regression risks, and state what verification you ran or will run next. Stop if the scope needs to change.

Review Prompt

Review the completed changes against the acceptance criteria. List any gaps, risks, or follow-up work. Summarize the evidence (tests/manual checks/diff review) and suggest the safest next improvement.

Assessment

  • Use the Capstone Rubric in RUBRICS.md for self-scoring.
  • Score from evidence, not memory.
  • Mark your lowest two dimensions.
  • Re-run one small capstone phase later focusing only on those two dimensions.

Self-Review Notes (Answer-Key Style for Solo Learners)

Strong capstone runs usually show:

  • clear scope and non-goals before execution
  • explicit acceptance criteria tied to verification
  • small, reviewable diffs with commit/checkpoint discipline
  • documented context-management decisions (continue vs restart)
  • a short, honest retrospective with one transferable workflow lesson

Common failure modes to catch early:

  • changing scope without updating criteria
  • trusting tool output without verification
  • skipping diff review until the end
  • mixing feature work into a refactor without stating it

Reflection Prompts

  • Which capstone phase felt most fragile, and why?
  • What evidence artifact was hardest to produce consistently?
  • What workflow would I standardize for my next real project?

Canonical Capstone Markdown

Capstone Project (Instructor-Ready)

The capstone synthesizes the full masterclass into a realistic, evidence-driven agentic development workflow. It is suitable for intermediate and advanced tracks, with a scaled-down variant for beginners.

TOC Mapping (Required)

  • TOC 1: Claude Code operations, planning/session control, permissions, MCP/subagents/hooks (optional), Git workflows
  • TOC 2: prompt framing, clarifying questions, proposal comparison, reliability habits
  • TOC 3: advanced refactor/review/orchestration and convergence
  • TOC 4: context engineering and maintenance
  • TOC 5: optional Codex CLI transfer comparison

Capstone Scenario (Default)

"Stabilize and extend a small service module in a real codebase under time pressure."

Learners receive a training repo containing:

  • 2 failing tests (one bug, one flaky or edge-case failure)
  • A messy module suitable for refactor
  • A small requested feature enhancement
  • Sparse docs and a changelog note to simulate real ambiguity

The challenge is to deliver a safe, verified patch set with a clear process record.

Deliverables (Required)

  1. CAPSTONE_PLAN.md (or equivalent note) containing:
    • Objective
    • Assumptions / clarifying questions
    • Acceptance criteria
    • Non-goals
    • Verification plan
  2. Code changes in a branch with small commits
  3. Verification evidence (test output, diffs, manual checks)
  4. CAPSTONE_RETRO.md (what failed, what changed, what to improve)
  5. 5-minute demo walkthrough (or recorded walkthrough)

Success Criteria (Learner-Facing)

  • Functional requirements met
  • Regressions minimized and checked
  • Process is reproducible and evidence-backed
  • Safety/tool decisions are explicit
  • Git history is understandable

This aligns with Anthropic guidance on explicit success criteria and testing/evaluation design. [Source: https://docs.anthropic.com/en/docs/test-and-evaluate/define-success] [Source: https://docs.anthropic.com/en/docs/test-and-evaluate/develop-tests]

Advanced Variants (Optional)

Variant A — MCP-Assisted Research

Require learners to use an MCP server for version-specific docs lookup and document trust boundaries. [Source: https://docs.anthropic.com/en/docs/claude-code/mcp] [Source: https://modelcontextprotocol.io/specification/2025-06-18]

Variant B — Subagent/Hook Pipeline

Require a planner/reviewer split and one automated hook gate. [Source: https://docs.anthropic.com/en/docs/claude-code/sub-agents] [Source: https://docs.anthropic.com/en/docs/claude-code/hooks]

Variant C — Codex CLI Transfer Compare

Repeat one capstone subtask in Codex CLI and write a short workflow comparison. [Source: https://github.com/openai/codex] [Source: https://platform.openai.com/docs/guides/codex]

Beginner Variant (Scaled)

  • Fix one bug only (no refactor)
  • Use instructor-provided acceptance criteria template
  • Require one diff review and one test run
  • 3-minute demo instead of 5

Capstone Prompts (Starter Templates)

Discovery Prompt

"Act as a senior engineer. Do not code yet. Inspect the repo and summarize the problem space. Ask clarifying questions, list assumptions, and draft measurable acceptance criteria and a verification plan. Keep scope tight and call out non-goals."

Execution Prompt

"Execute the approved plan incrementally. After each step, summarize the diff, run relevant checks, and compare results to acceptance criteria. Stop and ask if you need to expand scope."

Review Prompt

"Review the final changes as if for production: correctness, regression risk, tests, edge cases, security/safety concerns, and maintainability. Provide a release-readiness verdict with reasons."

These align with prompt clarity, evaluation design, and guardrail practices. [Source: https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview] [Source: https://docs.anthropic.com/en/docs/test-and-evaluate/develop-tests] [Source: https://docs.anthropic.com/en/docs/claude-code/security]

Assessment

Use RUBRICS.md Capstone Rubric (10 dimensions, 0-3 each).

Minimum evidence for a passing submission:

  • Plan with criteria and verification steps
  • At least one diff review artifact
  • Test/check output
  • Small commit history (or documented rationale for single commit)
  • Retro note with one process improvement

Facilitator Notes (Answer Key Style)

There is no single canonical code solution. Grade for:

  • Correct scoping and explicit success criteria first
  • Incremental execution with evidence
  • Ability to recover or re-scope when a plan fails
  • Clear explanation of tradeoffs and tool decisions

Weak but common outcomes to coach:

  • Large unreviewed diffs
  • “Looks good” without test evidence
  • Feature creep during refactor
  • External tool data used without validation
  • No rollback plan
